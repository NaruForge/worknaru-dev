# Worknaru Web UI

Codex Agent 생성·대화·보관, Workspace·Project 생성·조회·선택과 내장 Module 실행·Run 조회를 제공한다. CLI와 같은 Daemon의 데이터를 사용한다. 앱 탐색의 **Agent / Workspace / Module / 설정**으로 이동하며 **설정 → 연결**에서 Daemon 상태를 조회한다.

## Workspace·Project

**Workspace** 화면에서 업무 공간을 만들고 선택하면 소속 Project 목록을 확인할 수 있다. **Project 만들기**는 선택한 Workspace에 생성하며 입력 창에 소속을 표시한다. 중앙에는 선택한 항목의 이름·전체 ID·생성 시각·소속을 표시한다. 기존 공통 서버 플러그인을 준비한 환경에서 사용하며 Agent 생성이나 Provider 로그인은 필요하지 않다.

`#/workspaces?workspace=<ID>` 또는 `#/workspaces?project=<ID>`로 선택을 복원한다. Project의 Workspace는 조회된 소속에서 결정한다. 모바일 **목록으로**는 `pane=list`를 사용해 선택을 유지하고 브라우저 이력·새로고침에서도 복원한다. 잘못된 주소와 없는 항목은 안내 후 Workspace 목록으로 이동하며 일시적인 연결 실패는 선택을 유지한다.

목록은 화면 진입·선택·창 재활성화·수동 새로고침과 생성 성공 시 갱신한다. 생성 중 중복 제출을 막고, 결과가 불명확하면 입력을 보존하며 목록 확인을 안내한다. 같은 이름으로 성공을 추정하거나 자동 재시도하지 않는다. 다시 만들 때는 중복 생성 가능성을 확인하고 명시적으로 제출한다.

이 선택은 탐색 상태이며 Agent 소속·cwd·실행 맥락을 변경하지 않는다. 기능 간 이동 중 Agent 초안과 미저장 설정을 보존하고 **작업으로 돌아가기**는 설정에 들어오기 전 기능으로 복귀한다. Workspace 데이터·입력은 localStorage에 저장하지 않는다.

실제 교차 검증은 `node apps/web/test/workspace-browser.mjs`로 실행한다. 격리된 관리형 Daemon에서 CLI 생성 → Web 조회·생성 → CLI 조회 → 정상 재시작 후 데이터·선택 보존을 확인한다. 최초 setup이 빌드하며 별도 선행 빌드는 필요 없다. Provider를 호출하지 않고 Windows CI의 브라우저 작업에서도 실행한다. [검증 격리](../paseo-dev/README.md#검증-데이터-격리)를 따른다.

## 직접 실행

이름·로고·파비콘·대표 색상·관련 링크는 [공통 리브랜딩 설정](../../packages/branding/README.md)을 수정해 재빌드한다. 브랜드는 실행 중 바뀌지 않으며 서버 식별자와 상태 조회 동작은 유지한다.

표시 이름은 한글과 일반 공백을 지원하고, 이미지 입력은 고정 파일명, 링크 입력은 ASCII URL로 제한한다. 기본값을 포함한 데이터 루트의 폴더명은 영문·숫자·`-_.`만 허용한다. 경로 오류가 나면 [저장 위치 설정](../paseo-dev/README.md#저장-위치-설정)에 따라 지원되는 별도 절대경로를 지정한다.

저장소 루트에서 실행한다.

```powershell
pnpm install --frozen-lockfile
pnpm exec worknaru agent setup
pnpm exec worknaru dev start
```

`agent setup`은 정지된 개발 환경에서 최초 한 번 실행한다. Codex 설치·로그인이 필요하다. 준비 완료 뒤 같은 PC의 브라우저에서 `http://127.0.0.1:6868/`를 연다. 터미널을 닫아도 실행은 유지된다. 종료는 `pnpm exec worknaru dev stop`이다. 문제 진단은 `doctor`, CLI 조회는 `status`를 사용한다.

## Agent와 작업하기

1. **새 Agent**에서 이름·작업 폴더·Codex 모델을 선택한다. 작업 폴더는 빈 입력으로 시작한다. Daemon 컴퓨터의 영문·숫자·`-_.` 폴더명으로 된 공백 없는 절대경로를 입력한다. 기존 부모를 기준으로 경로 후보를 찾고 유효한 폴더가 확인된 뒤 모델을 조회한다. 폴더를 바꾸면 이전 모델 선택을 지우며 새 조회가 끝나야 생성할 수 있다.
2. 왼쪽 목록에서 Agent를 선택한다. 중앙에서 대화를 읽고 **Agent 상세 정보**에서 모델·작업 폴더·ID를 확인한다.
3. 메시지를 적고 **보내기** 또는 Enter를 누른다. Shift+Enter는 줄바꿈이다. 한글 조합 중 Enter는 전송하지 않는다. 접수 후 대기 상태와 응답을 자동 갱신한다.
4. 같은 창에서 다음 메시지를 보내 대화를 이어간다. **이전 대화 불러오기**로 앞선 기록을 읽는다. 탭을 다시 열어도 Daemon에 저장된 Agent·이력을 조회할 수 있다.
5. 작업을 끝내면 목록 행의 **보관 아이콘** 또는 채팅창 우측 상단의 **보관**을 누른다. 하위 Agent, 중단될 작업, 취소할 대기 메시지를 확인한 뒤 **확인하고 보관**한다. 선택하지 않은 Agent도 목록에서 보관할 수 있으며 현재 대화·초안은 유지한다. 목록의 **보관함**에서 다시 기록을 읽을 수 있다. 선택한 Agent를 보관하면 입력창 대신 보관 안내를 표시하며 파일을 삭제하지 않는다.

**설정 → Agent 동작**에서 CLI와 공유하는 전송 방식을 변경한다. 현재 방식은 메시지 입력창에서 계속 확인할 수 있다. 변경은 저장 후 새로 접수한 메시지부터 적용하며 접수된 대기와 재시도 요청의 방식은 유지한다. 대기열은 성공한 작업 뒤에 순서대로 실행하고 탭을 닫아도 유지된다. 추가 지시는 Paseo 기본 동작을 따르며, 적용할 수 없으면 진행 중인 작업을 중단하고 새 요청을 시작할 수 있다.

앱 탐색의 **Agent / Workspace / Module / 설정**은 아이콘으로 표시한다. 마우스를 올리면 브라우저 기본 툴팁으로 이름을 볼 수 있으며 Tab과 Enter로도 이동할 수 있다. 설정에 미저장 변경이 있으면 정보 표시가 붙고 이름이 **설정 (미저장)**으로 바뀐다. 설정 화면에서도 변경 상태를 글자로 확인할 수 있다. 작은 화면에서는 앱 탐색이 위쪽에 표시된다.

저장하지 않고 이동한 전송 설정은 **미저장**으로 표시하고 같은 탭에 유지한다. **저장**으로 반영하거나 **변경 취소**로 서버의 최신 확인 값으로 되돌린다. 새로고침·탭 종료에는 브라우저 경고를 요청하며 미저장 편집은 다시 열었을 때 유지되지 않는다. 다른 CLI/Web에서 설정을 바꾸면 충돌을 안내한다. **최신 설정 다시 불러오기**는 현재 편집 내용을 대체한다.

대화 아래 **메시지 실행 상태**에서 상태·내용·실행 전 취소를 확인한다. 실패·취소·결과 불명확 시 자동 실행이 멈춘다. 추가 지시가 새 요청으로 교체되며 이전 턴만 취소된 경우에는 새 요청을 계속 처리한다. 기록을 확인한 뒤 **남은 대기열 재개**를 누른다. `uncertain` 요청은 **기록 확인 후 실행 포기**로 취소 처리한 뒤 재개할 수 있다. 현재 작업이 진행 중이면 먼저 완료·권한 처리·보관을 선택한다. 불명확한 요청을 자동으로 재전송하지 않는다.

전송 실패·취소 시 입력을 남기며, 다시 **보내기**를 누르면 새 요청으로 접수한다. 통신 장애로 접수 여부가 불명확한 동안은 같은 요청 ID로 결과를 확인해 중복 실행을 막는다. **기록 확인 후 실행 포기**로 취소된 것이 확인되면 같은 내용도 새로 전송할 수 있다.

권한 요청은 대화 아래 카드에 표시된다. 실행 내용을 읽고 승인·거부를 선택한다. 질문에는 추천 선택지나 직접 입력으로 답하고, 여러 답은 쉼표로 구분한다. 실패 시 입력 내용을 유지한다. CLI에서 처리한 권한은 다음 조회에 반영된다. 보관 영향이 바뀌거나 일부 보관에 실패하면 **보관 대상 다시 확인**으로 최신 대상을 확인한다. 전송 설정이 다른 화면에서 변경되었다면 **최신 설정 다시 불러오기** 후 저장한다.

같은 Agent는 Worknaru CLI/Web으로 조작한다. 외부 Paseo 클라이언트가 같은 Agent를 동시에 변경하는 경우의 전송·보관 경쟁은 지원하지 않는다.

같은 탭에서 다른 Agent나 설정으로 이동해도 Agent별 초안·불명확한 전송의 요청 ID·추가로 불러온 대화와 읽던 위치를 유지한다. **작업으로 돌아가기**는 이전 Agent·활성/보관함 선택으로 복귀한다. 작은 화면의 **Agent 목록으로**도 초안을 유지한다. 새로고침·탭 종료 후 초안과 읽던 위치는 복원하지 않으며, 서버에 저장된 대화·대기열은 남는다. URL은 Agent 선택·보관함·설정 섹션을 표현하고 브라우저 뒤로/앞으로 및 기존 Agent 링크를 지원한다.

**설정 → 화면**에서 밝게·어둡게·시스템 테마를 선택한다. 목록과 데스크톱 상세 패널의 구분선을 드래그하거나 Tab으로 선택한 뒤 방향키·Home·End로 크기를 조절할 수 있다. **목록 접기/펼치기**, **Agent 상세 정보/상세 정보 닫기**로 작업 공간을 조정한다. 테마·너비·접힘은 이 브라우저에서 서버 ID별로 저장하며 **배치 초기화**는 패널 선호를 기본값으로 돌린다. 작은 화면에서는 저장된 너비 대신 화면 폭에 맞춰 표시한다. 저장이 차단되어도 현재 탭에서는 사용할 수 있다.

폼에는 label과 키보드 포커스를 제공하고 상태·오류는 텍스트로 안내한다. 대화·도구 출력은 HTML로 실행하지 않고 텍스트로 표시한다.

가장 작은 확인 순서는 다음과 같다.

1. **설정 → 연결 → 상태 확인**을 눌러 정상 응답 안내, 서버 ID와 `0.8.0` 버전 표시를 확인한다.
2. 브라우저 탭을 유지한 채 터미널에서 `pnpm exec worknaru dev stop`을 실행한다.
3. 열린 화면의 버튼을 다시 눌러 연결 오류 안내와 서버 정보가 비워지는 것을 확인한다. Daemon이 웹 파일도 제공하므로 이 단계에서는 페이지를 새로고침하지 않는다.
4. 다시 `pnpm exec worknaru dev start`를 실행하면 같은 탭에서 정상 조회를 재시도할 수 있다.

정상 관리 인스턴스가 실행 중이면 재사용한다. 다른 실행기가 포트를 점유하거나 소유권을 확인할 수 없으면 실행을 거부한다. 기존 `pnpm web:dev`는 터미널에 연결된 수동 검증용으로 유지하며 `stop` 또는 Ctrl+C로 종료한다. `dev start`, `paseo:verify`, `web:dev`는 같은 포트를 사용하므로 함께 실행하지 않는다. 오류·로그 위치와 운영 분리 기준은 [개발 환경 안내](../paseo-dev/README.md)를 따른다.

## Module 실행과 기록

앱 탐색의 **Module**에서 **독립 실행** 또는 이름·ID로 표시된 Workspace/Project를 선택합니다. **분석할 텍스트**를 입력하고 **실행**하면 `text-stats`의 글자 수와 줄 수를 확인합니다. 빈 문자열도 실행할 수 있고 최대 입력은 100,000 UTF-16 단위이며, 글자 수는 줄바꿈을 포함한 Unicode 코드 포인트 수입니다.

**이전 실행**은 선택한 대상의 기록만 표시합니다. 기록을 선택하면 입력·상태·결과·Run ID·생성 시각을 다시 확인합니다. 선택한 대상과 Run은 `#/modules?project=…&run=…` 같은 URL로 복원하며 새로고침·정상 서버 재시작 후에도 서버 기록을 다시 조회합니다. 접수/실행 중 기록은 화면이 열려 있는 동안 자동 조회하고, 연결 오류에는 **다시 불러오기**, 다른 CLI/Web 실행에는 **기록 새로고침**을 사용합니다.

응답을 확인하지 못하면 입력을 잠그고 요청을 보존합니다. **같은 요청으로 다시 확인**은 같은 ID·입력·대상을 보내 중복 실행을 막습니다. 실패와 결과 미확정은 성공과 구분하며 자동 재실행하지 않습니다. **실행**을 다시 누르는 것은 새 실행입니다. 대상별 초안·확인 중인 요청은 같은 탭의 화면 이동까지만 유지하며 새로고침·탭 종료 후에는 복원하지 않습니다. 입력은 브라우저 영속 저장소에 쓰지 않습니다. 새로고침 뒤에는 이전 실행 기록을 먼저 확인해 주세요.

화면은 기존 Core `modules`/`workspace` API와 공통 UI 부품을 조립합니다. Provider·새 서버·저장 구조를 추가하지 않습니다. `Modules.stories.tsx`에 빈 상태·로딩·오류·응답 유실·실패·미확정·실행 중 예제를 제공합니다. `pnpm ui:verify:functional modules.spec.ts`로 키보드·접근성·반응형 동작을 확인하고, `node apps/web/test/workspace-browser.mjs`는 세 실행 대상의 CLI/Web 교차 사용과 재시작 후 Run 복원을 실제 전용 Daemon에서 검증합니다.

[Agent 세션](src/features/agents/useAgentSession.ts)과 [Agent 화면](src/features/agents/AgentScreen.tsx)은 Core의 `agents` 메서드를, [통합 설정](src/shell/SettingsView.tsx)은 공유 설정과 `getDaemonStatus()`를 호출한다. 공통 표현은 [UI 패키지](../../packages/ui/README.md)를 조립한다. [App Shell 결정](../../docs/adr/0010-app-shell-and-work-context.md)에 상태 수명과 배포 경계를 설명한다.
- [Vite 빌드](build.mjs)는 별도 TypeScript 검사 후 화면·Core·Adapter·Paseo Client를 브라우저용 `dist/app.js`에 함께 묶는다. `index.html`, `styles.css`와 허용된 브랜드 자산만 배포하며 해시 디렉터리·Storybook·connection.json을 빌드에 포함하지 않는다.
- 개발 실행 프로그램은 [지정 데이터 루트](../paseo-dev/README.md#저장-위치-설정)의 `tmp/web-*`에 허용된 웹 자산을 복사한다. 자신이 시작한 Daemon의 소유권·서버 ID를 확인한 뒤 이 폴더의 `connection.json`에 공개 대상 ID와 예상 서버 ID를 쓴다. 비밀번호·Provider 인증 정보·Daemon 설정·로그는 제공하지 않는다. 임시 웹 폴더는 해당 실행 종료 시 정리한다.
- 브라우저는 이 설정을 읽고 페이지와 같은 호스트의 `/ws`로 접속한다. Daemon이 정적 파일 제공과 WebSocket 접속을 모두 맡으며 별도 Worknaru API 서버는 없다.
- 기본 조회 제한 시간은 5초다. 조회 중 버튼을 비활성화하고, 완료 후 조회용 연결을 정리한다. 연결 실패를 원격 프로세스 종료의 확정 판정으로 사용하지 않는다.

현재 실행 명령은 `127.0.0.1`에만 바인딩하는 로컬 개발용이다. 인증 입력·대상 선택·원격 배포는 지원하지 않는다. Web Crypto를 사용하므로 localhost 또는 HTTPS 환경이 필요하다. Agent 세션은 약 1.5초마다 조회하며 중복 조회를 막는다. 대기열 실행과 Provider 이벤트 관찰은 Daemon 플러그인이 담당한다. 따라서 탭 종료는 작업 종료를 뜻하지 않는다.

## 검증

Agent·대기열·권한·보관과 브라우저 사용 흐름의 검증 근거는 [Issue #17](https://github.com/NaruForge/worknaru-dev/issues/17)에 둔다. 기본 전체 흐름, CLI와 Web 간 후속 대화·설정 공유, 권한 승인·거부, 한글 조합 Enter·줄바꿈, 보관 후 전송 금지, 작은 화면과 재접속을 확인한다. 실제 Codex 검증에는 Provider 사용량이 발생한다.

실제 Web–Provider 연결에 영향을 주면 소유권과 영향을 확인한 관리형 환경을 종료하고 빈 개발 포트에서 `pnpm ui:live`를 실행한다. 실제 생성·대화·후속 대화·새로고침 후 이력·보관과 CLI/Web 교차 사용을 재현한다. [실행기](test/live-browser.mjs)가 자체 격리 환경을 만들고 [브라우저 흐름](test/agent.browser.mjs)에 외부 작업 폴더와 캡처 경로를 전달한다. 캡처는 해당 외부 실행 폴더에 남긴다. IME·줄바꿈·작은 화면·포커스·초안·테마·설정 충돌의 일반 동작은 기존 Vitest와 Storybook 브라우저 검사로 선택한다.

개별 화면은 관련 Web 테스트·정적 검사와 `pnpm ui:verify:functional <spec> --grep <흐름>`으로 선택 검증한다. 이 명령은 Storybook을 빌드하고 기능·키보드·접근성을 검사하며 이미지 비교는 제외한다. 전체 `pnpm test`와 `pnpm ui:verify`는 공통 UI 변경 및 최종 UI 회귀에 사용한다. Docker 준비는 필요하지 않다. 브라우저가 없으면 `pnpm --filter @worknaru/web exec playwright install chromium`을 먼저 실행한다. 빌드 재사용 명령, 전체 검증 조건, Windows CI 기준 이미지의 검토·갱신과 AI 조립 평가는 [UI 표준](../../docs/ui-design.md#실행과-검증)을 따른다. `pnpm ui:storybook`으로 실제 부품과 상태별 견본을 확인한다. 실연동은 [변경별 선택 기준](../paseo-dev/README.md#검증-선택)을 따른다.

실제 브라우저의 정상 조회·종료 후 실패·소켓 정리와 loopback 응답 서버를 사용한 인증 오류·대상 불일치·시간 초과 검증의 근거는 [Issue #9](https://github.com/NaruForge/worknaru-dev/issues/9)에 둔다. Paseo `0.8.0` 전환 후 같은 경로를 재검증한 근거는 [Issue #11](https://github.com/NaruForge/worknaru-dev/issues/11)에 연결한다.

`pnpm ui:live`는 Windows에서 빈 개발 포트를 확인하고 [검증 전용 외부 루트](../paseo-dev/README.md#검증-데이터-격리)의 실행별 독립 데이터로 실제 Web 흐름·CLI/Web 교차 대화를 검증한 뒤 자신이 시작한 환경을 종료한다. Codex 로그인과 Provider 사용량이 필요하며 결과·실패 화면은 해당 실행 폴더에 남는다. 기본 개인 데이터 루트를 정리하거나 기존 프로세스를 종료하지 않는다.

오래된 탭의 전송 차단은 `pnpm ui:verify:functional sdk-identity.spec.ts`로 선택한다. `Verification/Connection` story는 Core 주입 없이 실제 App의 bootstrap과 고정 SDK를 실행하고, 브라우저 검사가 접속 설정·WebSocket 응답만 제공한다. 정상 ID의 생성·전송을 확인한 뒤 ID 변경 시 송신 RPC 부재, 초안·URL 유지, 수동 새로고침 후 선호 초기화를 검사한다. Provider·실제 Daemon 없이 실행하며 기존 Storybook 소스 빌드를 사용한다. 새 checkout/의존 패키지 변경 시 위 UI 표준의 선행 빌드를 적용한다. 이 검사는 실제 Daemon reset 완료 검증과 구분한다.

## 전체 초기화 후 새로고침

서버 데이터와 브라우저 상태의 저장 위치·수명은 [데이터 저장 위치](../../docs/data-storage.md)에 모아 설명한다. 개발자 도구에서 확인할 키는 [브라우저 저장 위치](../../docs/data-storage.md#브라우저-저장-위치)를 참고한다.

서버를 정지하고 CLI의 `dev reset --yes`를 실행한 뒤 `agent setup`과 `dev start`로 새 환경을 만든다. 열린 화면은 그대로 두며 자동 이동이나 이전 요청 자동 재전송을 하지 않는다. 오래된 탭은 예상 server ID가 달라 새 서버에 Agent 요청을 보낼 수 없으며 새로고침 안내를 표시한다.

새로고침하면 새 `connection.json`의 server ID를 읽어 초기 Agent 목록으로 이동한다. 이전 서버의 테마·레이아웃과 과거 전역 UI 저장값을 정리하고 기본값으로 시작한다. 초안·대화 캐시·미저장 설정은 복원하지 않는다. reset 없이 정상 stop/start만 하면 server ID가 같으므로 테마·레이아웃을 유지한다.

## 데이터 관리

**설정 → 데이터 관리**에서 현재 실행 PC와 데이터 루트의 설정 출처, 전용 설정·Agent 등록·메시지/대기열 DB·로그·worktree·임시 파일의 위치와 존재 상태를 확인한다. 실제 Agent 작업 폴더와 개인 Paseo·Codex 저장소는 보존 영역으로 구분한다. 작업 폴더가 전용 루트 안에 있으면 삭제 영역으로 표시한다. 자세한 저장 책임은 [데이터 저장 위치](../../docs/data-storage.md#설정에서-데이터-관리)를 따른다.

**열기**는 실행 PC의 Windows 탐색기에서 디렉터리를 연다. 파일은 상위 폴더를 연다. 없는 경로나 확인할 수 없는 항목은 비활성화하며, 조회 후 경로 변경도 서버에서 다시 검사한다. 브라우저의 Local Storage·탭 메모리는 설명만 제공한다.

**초기화 대상 확인**은 삭제 예정 항목과 보존 범위를 보여준다. **삭제하고 다시 시작**을 확인하면 모든 Agent 작업을 종료하고, 전용 데이터 전체를 삭제한 뒤 새 기본 환경을 시작한다. 이 탭의 초안·미저장 설정도 폐기한다. 확인 없이 삭제하거나 응답 유실을 이유로 삭제를 재전송하지 않는다. 새 서버와 해당 요청의 완료가 확인되면 자동 새로고침하며, 다른 오래된 탭은 수동 새로고침이 필요하다.

요청이 명시적으로 거부되면 오류를 고친 뒤 새 미리보기를 받는다. 결과를 확인하는 동안 브라우저 뒤로 가기나 주소의 hash가 바뀌어도 데이터 관리 화면을 유지한다. 실행 중 연결이 끊기거나 2분이 지나도 재시작을 확인하지 못하면 성공으로 표시하지 않는다. **재시작 결과 다시 확인**을 사용하거나 실행 PC의 같은 checkout·데이터 루트에서 `pnpm exec worknaru doctor`로 진단한다. 삭제 실패 시 [CLI 초기화 절차](../cli/README.md#사용자-데이터-전체-초기화)에 따라 정지·소유권·잠금을 확인하고 재시도한다.

연결은 기존 Daemon의 `development.data` RPC와 관리 실행기의 named pipe를 사용한다. 별도 HTTP 서버·포트·백그라운드 서비스를 추가하지 않는다. 이 앱의 개발 관리 통신은 제품 Core/Runtime 계약 밖에 있으며, 기존 서버 ID·버전 확인을 적용한다. 관리형 Windows `dev start`와 활성화된 Agent 서비스가 필요하다.

데이터 화면 문구·표시는 관련 고정 데이터 테스트로 확인하고 공통 UI 변경 및 병합 검증은 UI 표준을 따른다. 실제 설정 공유·연결 복구·초기화·재시작 경계를 변경하면 관리 환경을 정지한 뒤 `node apps/web/test/data-browser.mjs`로 검사한다. 최초 setup이 한 번 빌드하므로 별도 선행 빌드는 필요 없다. 실행기 수명·실패 정리에도 영향을 주면 `pnpm dev:verify`를 추가한다. 테스트 전용 외부 루트에서 저장된 비기본 설정의 재시작 보존, 두 차례 초기화와 요청 ID별 완료, 새 서버 ID/기본 선호, 외부 파일 보존, 다른 탭의 설정 저장 거부를 확인한다. 모델 조회·Agent 생성·Provider 대화를 하지 않으며 로그인/사용량이 필요 없다. CLI 명령·송신 RPC·등록 상태와 reset 전 로그를 실행 폴더에 남겨 비의존 경로를 확인한다. `WORKNARU_TEST_ROOT`를 지원한다. 폴더 열기는 단위 테스트에서 실행 대상을 검사하며 실제 탐색기 창은 자동 검증에서 열지 않는다.
