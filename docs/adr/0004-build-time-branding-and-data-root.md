## Context

운영자는 자신의 브랜드와 원하는 저장 위치로 서비스를 사용할 필요가 있다. 초기 개발에서는 브랜드별 동작 분기, 여러 설정 출처, 이름 호환과 데이터 자동 이전이 이후의 디버깅·검증 비용을 늘릴 수 있다. CLI·웹의 표시 처리는 Core·Runtime·Adapter의 업무·실행 계약과 분리되어 있다.

## Decision

- `packages/branding`의 manifest와 정적 자산을 검증해 읽기 전용 브랜드 정의를 생성한다. 웹·CLI는 같은 빌드 결과를 사용하며 실행 중·사용자별 전환은 제공하지 않는다.
- 사용자 표시 이름·로고·파비콘·대표 색상·고정 링크 항목만 지원한다. 실제 CLI 명령, 환경 변수 접두사, API·패키지·내부 식별자는 브랜딩 대상으로 삼지 않는다.
- 개발 실행기는 `WORKNARU_DATA_DIR` 하나를 시작 시 해석한다. 미설정 시 기존 기본 루트를 사용하고 명시한 값이 잘못되면 실패한다. 하위 경로는 공통 함수로 계산한다.
- 브랜드에서 경로·target ID·server ID·인증 값을 유도하지 않는다. Core·Runtime·Adapter에 브랜드나 파일 시스템 설정 책임을 추가하지 않는다.
- 웹 접속 설정은 데이터 루트의 별도 임시 웹 디렉터리에 생성한다. 허용된 정적 웹 자산과 공개 접속 설정만 제공하며 해당 실행 종료 시 정리한다.
- 기존 데이터·설정·식별자를 자동 이전하거나 덮어쓰지 않는다. 개별 저장 경로와 OS 서비스 등록 변경은 제공하지 않는다.

## Consequences

브랜드가 업무 로직에 영향을 주지 않으며 기본/사용자 브랜드와 기본/지정 루트의 작은 조합으로 검증할 수 있다. 브랜드 변경에는 재빌드와 웹 개발 환경 재시작이 필요하다. 운영자가 보는 명령과 환경 변수에는 원본 제품 이름이 남는다.

실행기·상태 조회·검증은 같은 경로 계산을 사용해야 한다. 잘못된 경로·권한·기존 설정 충돌을 초기에 드러내고 진단은 기계 판독용 stdout과 분리한다. 외부 도구의 저장소와 향후 Module·Workspace 저장 모델은 이 결정의 보장 범위가 아니다.
