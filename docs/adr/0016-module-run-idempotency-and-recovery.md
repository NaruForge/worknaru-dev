# ADR 0016: Module 접수 멱등성과 중단 후 결과 미확정

- 날짜: 2026-09-16
- 상태: Accepted
- 관련 작업·승인: [#55](https://github.com/NaruForge/worknaru-dev/issues/55). 사용자가 명시적 실행 맥락·요청 ID·영속 기록·재시작 시 자동 재실행 금지 계획의 구현을 승인했다.

## Context

첫 내장 Module을 실행하려면 통신 응답의 성공과 실제 실행 결과의 확정을 구분해야 한다. 요청 응답이 유실되거나 실행과 결과 저장 사이에 서버가 종료되면 클라이언트는 실행 여부를 알 수 없다. Workspace·Project 소속은 ADR 0015를 따르며 cwd·파일 권한과 분리한다.

## Decision

호출자가 생성한 요청 UUID를 전용 Module 저장소 전체에서 유일하게 사용한다. 동일 ID·Module·정규화 입력·맥락의 재접수는 기존 Run을 반환하며 다른 내용은 충돌로 거부한다. 구현 버전은 최초 접수 시 기록한다. 통신 계층은 자동 재시도하지 않는다.

Core가 입력과 대상 존재·소속을 확인한 뒤 `accepted`를 저장하고, `running` 저장 후에만 앱이 주입한 신뢰된 내장 구현을 호출한다. 정상 반환과 결과 검증 성공은 `succeeded`, 실행 또는 결과 검증 예외는 `failed`다. 결과 저장 실패는 성공으로 반환하지 않는다. 서비스 시작 시 남은 `accepted`·`running`은 `uncertain`으로 바꾸고 재실행하지 않는다. 정상 종료는 접수를 막고 현재 호출을 기다린다.

Run은 앱 수준·Workspace 직접 실행·Project 실행별 정확한 맥락으로 조회한다. Workspace 목록이 하위 Project 실행을 암묵적으로 합치지 않는다. 이 구분은 조회 범위이며 다중 사용자 접근 제어가 아니다.

서버 앱은 `module-runs.sqlite`에 기록을 보관한다. 업무 구조 DB와 실행 기록의 스키마·수명을 분리하고 기존 Agent 대기열을 Module 실행기로 사용하지 않는다. 한 전용 Daemon에서 한 Module 서비스를 운영한다. 저장 루트 버전은 2이며 이전 버전은 기존 reset 절차가 필요하다. 자동 변환·초기화는 하지 않는다.

## Consequences

응답 유실 뒤 같은 ID로 확인해도 한 번 접수된 작업이 중복 실행되지 않는다. 실행하지 못한 채 접수만 남은 경우에도 자동 복구 실행을 포기한다. 사용자가 새 ID로 실행하면 별도 Run이므로 부작용이 있는 Module을 도입할 때는 추가 확인 정책이 필요하다.

외부 시스템의 부작용과 SQLite 기록을 하나의 트랜잭션으로 보장하지 않으므로 exactly-once 완료를 약속하지 않는다. `uncertain.finishedAt`은 결과가 미확정으로 판정된 시각이며 실제 실행 종료 시각이 아니다. 실행 취소·재개·사용자 코드 설치·장시간 작업 스케줄링은 이 구현에서 제공하지 않는다.
