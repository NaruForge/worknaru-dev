# ADR 0015: 업무 소속과 독립 Module의 실행 맥락

- 날짜: 2026-09-15
- 상태: Accepted
- 관련 작업: [#49](https://github.com/NaruForge/worknaru-dev/issues/49), 선행 평가 [#48](https://github.com/NaruForge/worknaru-dev/issues/48)
- 승인 근거: 사용자가 제안의 수용 여부를 판단하도록 요청했고, 수정 수용·비수용 판단과 공식 문서·ADR 반영 계획에 “진행하세요”라고 지시했다. [판단·승인 기록](https://github.com/NaruForge/worknaru-dev/issues/49#issuecomment-5676944858)
- 계약: [용어집](../glossary.md), [아키텍처의 제품 계약](../architecture.md#제품-개념과-현재-구현의-관계). 관리·Run API·저장·UI 구현은 후속 범위다.

## Context

#48은 Workspace·Project·Module의 관계를 평가했지만 공식 문서에는 상세 관계가 설계 중으로 남아 있었다. 이후 구현에서 업무의 소속, 재사용할 기능, 실행 대상과 기록의 귀속을 다르게 해석하지 않도록 공통 계약이 필요하다.

Project를 기간이나 실행 횟수로 구분하면 독립적인 변환을 반복하는 경우까지 Project로 만들기 쉽다. 반대로 짧은 보고서 작업도 자료 비교·검토·결정을 후속 작업에 재사용할 수 있다. 기록은 단독 실행에도 필요하므로 기록의 존재만으로도 구분할 수 없다.

Workspace가 정리 기능을 제공한다는 사실은 Project 소속을 필수로 할지 결정하지 않는다. 이 선택은 관리 책임의 명확성과 첫 업무를 시작할 때의 부담을 비교해야 한다. 또한 공통 설정을 구성하는 것과 하위 업무에 자동 적용하는 것은 다른 결정이다.

## Decision

1. **Project는 정확히 하나의 Workspace에 소속시킨다.** 무소속을 허용하면 첫 Project 생성이 간단하지만 무소속 업무의 탐색·소속 전환도 설계해야 한다. 다중 소속은 여러 관점의 정리에 유용하지만 관리·설정·삭제 책임이 복잡해진다. 초기에는 관리 위치가 명확한 단일 소속을 선택하며 중첩은 도입하지 않는다. Workspace는 이 업무 구조의 최상위이고 앱의 모든 실행을 감싸는 필수 부모는 아니다.
2. **Module은 독립 기능으로 두고 Workspace·Project에서 참조해 사용한다.** 공간별 복제나 소속으로 기능을 재사용하면 정의·버전과 사용자 데이터를 혼동하기 쉽다. 사용 관계, 설정·지속 상태, 실행 기록·결과를 구분한다. 목록 추가는 실행의 선행 조건이 아니며 실행 자격·입력·권한은 별도로 확인한다.
3. **Standalone / Workspace / Project 실행 맥락을 명시한다.** 모든 실행에 전체 소속 계층을 요구하면 간단한 처리에도 불필요한 공간·업무를 만들어야 한다. 단독 실행의 기록·결과는 앱 수준에서 다시 찾을 수 있게 하고 숨은 Workspace·Project를 만들지 않는다. Project 실행의 Workspace는 Project에서 도출하며 불일치를 거부한다. 각 Module은 필요한 맥락을 제한할 수 있다.

Project의 구분 기준은 같은 목표·대상의 자료·대화·결과·결정을 함께 관리하고 후속 작업에서 재사용할 필요다. 이미 축적된 이력, 긴 기간, 여러 번의 실행을 필수 조건으로 삼지 않는다. Workspace 공통 설정의 자동 상속·동기화, 물리 저장·공개 API·세션·권한의 상세 모델은 이번 선택에서 정하지 않는다.

이 결정은 기존 ADR을 대체하지 않는다. Agent 전송·탐색·저장·초기화 계약은 유지하고, 이전에 보류한 업무 도메인 계약을 추가한다. 과거 #48의 평가 기록도 당시 범위와 의미를 유지한다.

## Consequences

사용자는 단독 처리에서 시작해 맥락을 함께 관리할 필요가 생기면 Project를 사용할 수 있다. 같은 기능을 여러 업무에 재사용하면서 자료·상태·결과가 자동으로 섞이지 않게 한다. Agent와 직접 대화하거나 앱 수준 안내를 사용하는 데 전체 소속 계층을 요구하지 않는다.

단일 소속 때문에 첫 Project에도 Workspace를 정해야 한다. 생성 안내에서 공간과 업무를 함께 식별하도록 하며 무소속·다중 소속과 이동·공유의 상세 모델은 후속 요구로 검토한다. 단독 실행의 재조회, 사용별 데이터 분리, 명시적 설정 적용을 지원하는 비용은 후속 구현에 남는다.

정의·관계·실행 맥락을 채택해도 API·UI·저장이 구현된 것은 아니다. 로컬 폴더·Git 저장소·Agent cwd·Paseo 개념과의 매핑, Module 배포·버전, 공유 상태와 설정 상속은 해당 기능을 구현할 때 별도로 설계한다. 업무 소속을 외부 파일 삭제나 접근 권한 상속으로 확대하지 않는다.
