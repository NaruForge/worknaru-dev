# Paseo Adapter 초기 설계 초안

- 작성일: 2026-09-10.
- 문서 성격: 초기 지원 범위와 동작을 검토하기 위한 설계 초안.
- 관련 자료: [Paseo CLI 기능 참고](paseo-cli-capabilities.md), [Runtime 의존 경계 ADR](adr/0001-runtime-interface-and-paseo-adapter.md).

이 문서는 구현 전 검토할 기술 설계다. 구현 작업의 범위·진행 상태·검증 증거는 [프로젝트 기록 규약](project-records.md)에 따라 관리한다.

## 목표

Worknaru CLI의 주 사용자인 AI Agent가 실행 기반의 상태를 확인하고, 필요한 에이전트 세션을 생성·조회·재사용하며, 작업의 진행과 결과를 확인하고, 중단·보관할 수 있도록 한다. 이는 사용자가 플랫폼 안에서 AI Agent와 함께 Module을 개발하는 데 필요한 첫 실행 기반이다.

Module은 외부 서비스, 로컬 서비스, 사용자 검수, AI Agent의 참여를 함께 구성할 수 있는 업무 기능이다. 이 초안의 에이전트 세션과 개별 작업은 Module 전체의 생명주기를 뜻하지 않는다.

## 초기 적용 범위

- 현재 PC에서 사용 중인 개인용 Paseo와 운영을 분리한 Worknaru 전용 Daemon 하나를 대상으로 한다. 같은 Windows 사용자 계정, 사용자 홈, 파일 접근 권한과 기존 인증 정보를 공유할 수 있다. 개발 검증용 주소·버전과 실행 방법은 [개발 환경 안내](../apps/paseo-dev/README.md)를 참고한다.
- 기존 디렉터리와 Paseo Workspace를 지정하거나 재사용하는 흐름부터 지원한다. 필요한 경우 해당 디렉터리의 실행 작업 공간을 생성한다.
- Worknaru Workspace와 Paseo Workspace의 대응 관계는 별도 설계 대상으로 둔다. 디렉터리 경로는 대상 Daemon에서 해석한다.
- Core가 Module·Workspace와 실행 세션의 관계 및 생성·재사용·정리 정책을 담당한다. Adapter는 Paseo 호출과 결과 변환을 담당한다.
- 구체적인 패키지 수, CLI 명령 문법, TypeScript 타입 이름은 이 초안에서 확정하지 않는다.

## 기존 Paseo와의 운영 분리

사용 중인 Paseo와 Worknaru 전용 Daemon의 실행·설정·세션 저장 위치·접속 대상을 분리한다. 사용자 홈, 파일 접근 권한, Provider의 설정·인증은 기존 환경을 함께 사용할 수 있다. 아래는 설계 요건이다. 개발 환경의 운영 분리 검증 범위와 근거는 [Issue #1](https://github.com/NaruForge/worknaru-dev/issues/1)에서 관리한다.

| 분리 대상 | 요건 |
| --- | --- |
| 설치와 버전 | Worknaru가 사용할 실행 파일·패키지 버전을 별도로 고정한다. 개인용 Paseo Desktop에 포함된 실행 파일의 업데이트에 의존하지 않는다. |
| Daemon 데이터 | 전용 `PASEO_HOME`으로 설정, 세션 기록, 로그 등 저장 경로를 분리한다. 로그·worktree 등의 개별 경로 설정이 기존 Paseo 경로를 가리키지 않는지도 확인한다. |
| 통신 경로 | 전용 주소·포트 또는 IPC 경로를 사용한다. MCP·서비스 프록시 등 함께 사용하는 리스너와 서비스 포트도 충돌 여부를 확인한다. |
| 접속 대상 | Adapter는 명시한 전용 Daemon에만 접속한다. 설정이 없거나 연결에 실패했을 때 기본 로컬 Paseo로 대체 접속하지 않는다. 확인 가능한 서버 식별자가 예상 대상과 다르면 작업을 거부한다. |
| 대상 선택 환경 | `PASEO_HOST`, `PASEO_HOME`, 부모 Agent 식별자와 로그 경로 등 대상 Daemon과 연결 관계를 결정하는 값은 전용 인스턴스에 맞춘다. 사용자 홈과 기존 Provider 설정·인증 정보는 공유할 수 있다. |
| 프로세스 제어 | Worknaru 전용 인스턴스가 생성한 프로세스와 자원만 제어·정리한다. 실행 중인 개인용 Paseo를 시작·중단·재시작하거나 그 세션을 수정하지 않는다. |

Paseo는 `PASEO_HOME` 또는 `daemon start --home`으로 Daemon 데이터 디렉터리를 바꾸고, 별도의 listen 주소를 설정할 수 있다. 이 문서의 전용 `PASEO_HOME`은 Daemon 설정·세션 데이터의 저장 위치이며, Windows 사용자 홈을 변경하거나 분리한다는 뜻은 아니다. [설정 문서](https://paseo.sh/docs/configuration.md)

별도 OS 계정, 파일 접근 권한 격리, 컨테이너·VM, Provider 홈·인증 분리는 요구하지 않는다. 기존 파일과 로그인 환경을 활용하면서 Daemon 인스턴스의 운영 충돌을 방지하는 범위로 설계한다.

운영 분리 검증에는 서로 다른 서버 식별자·Daemon 저장 경로·접속 주소 확인, 각 Daemon이 관리하는 세션 목록의 구분, 전용 인스턴스의 종료가 개인용 인스턴스에 영향을 주지 않는지 확인하는 절차를 포함한다. 구성·실행 전에 검증 대상과 방법을 정하며, 현재 개인용 인스턴스를 시험 대상으로 사용하지 않는다.

## 초기 필수 기능 제안

| 기능 | 최소 동작 | 설계할 핵심 의미 |
| --- | --- | --- |
| Daemon 상태 조회 | 설정된 대상의 응답·접속 결과와 확인 가능한 서버 정보 조회 | Daemon 상태, 클라이언트 연결 상태, 에이전트 상태를 구분한다. |
| 연결 관리 | 접속·인증, 연결 상태 조회, 제한 시간, 연결 해제 | 연결 해제는 에이전트 세션의 종료를 뜻하지 않는다. |
| 실행 환경 확보 | Provider 가용 상태와 모델·모드 확인, 실행 디렉터리·작업 공간 지정 및 재사용 | 같은 디렉터리를 쓰더라도 별도 작업 공간을 구분한다. 상태·목록 조회는 자원을 생성하지 않는다. |
| 세션 생성 | Provider·모델·모드·실행 위치를 지정하고 세션 식별자 반환 | 새 세션과 기존 세션 재사용을 구분한다. 하위 Agent 생성 시 호출자·부모 관계를 전달한다. |
| 세션 조회 | 목록·상세 상태·실행 중인 작업·최근 오류·권한 대기 조회 | 실행 작업 공간 등 필요한 범위로 조회하고, 존재하지 않는 세션과 조회 실패를 구분한다. |
| 후속 작업 전달 | 기존 세션에 요청을 전달하고 접수 결과 반환 | 요청 접수와 실행 완료를 구분한다. CLI를 다시 실행해도 같은 세션에 접근할 수 있어야 한다. |
| 진행·결과 관찰 | 상태·출력 이벤트 구독, 실행 이력 조회, 특정 작업의 결과 대기 | 성공·실패·취소·권한 대기·대기 시간 초과를 구분한다. |
| 권한 요청 처리 | 대기 중인 요청 조회·전달, 요청 ID에 대한 승인·거부 응답 | 권한 있는 사용자나 호출자의 결정을 전달한다. Adapter가 요청을 임의로 승인하지 않는다. |
| 현재 작업 중단 | 실행 중인 작업에 중단 요청을 보내고 결과 확인 | 중단 요청 전송과 실제 중단을 구분한다. 거절·시간 초과를 성공으로 처리하지 않는다. |
| 세션 보관 | 세션 실행 자원을 정리하고 기록 유지 | 영구 삭제와 작업 공간 보관을 구분한다. 부모 세션 보관이 하위 Agent에 미치는 영향도 확인한다. |

이 항목들은 하나의 Paseo Adapter가 제공할 기능 범위다. 기능마다 별도 패키지나 Adapter를 만드는 계획은 포함하지 않는다.

## Daemon 상태 조회 계약

에이전트가 작업을 시작하기 전에 실행 기반을 사용할 수 있는지 판단하도록 정보를 제공한다. 아래는 필드 이름까지 확정한 스키마가 아닌 반환 정보의 초안이다.

| 반환 정보 | 의미 |
| --- | --- |
| 대상과 확인 시각 | 어떤 Daemon을 언제 확인했는지 식별한다. 접속 자격증명은 출력하지 않는다. |
| 접속 결과 | 사용 가능한 응답, 연결 실패, 시간 초과, 인증 실패, 호환성 문제, 확인 불가를 구분한다. 확인되지 않은 원인을 추정하지 않는다. |
| 서버 식별자·버전 | 서버에서 확인한 값을 반환한다. 확인하지 못한 값은 미확인으로 표시한다. |
| 클라이언트 연결 상태 | Adapter의 연결 중·연결됨·연결 해제 등의 상태를 별도로 제공한다. |
| 로컬 실행 정보 | 신뢰할 수 있는 로컬 조회 경로가 있을 때 실행 여부 등을 보조 정보로 제공한다. 원격 대상이나 조회 불가 환경에서는 미확인으로 둔다. |
| 실패 정보 | 확인한 원인과 추가 확인에 필요한 정보를 Worknaru의 오류 형식으로 전달한다. |

설치된 CLI에서 `paseo status --help`와 `paseo daemon status --help`는 모두 로컬 Daemon 상태 조회를 설명한다. 따라서 로컬 `paseo status`의 결과로 설정된 원격 Daemon의 상태를 대신 판단하지 않는다.

SDK의 `getConnectionState()`는 현재 클라이언트의 연결 상태를 반환한다. 첫 구현의 확정된 필드와 의미는 [Runtime 계약](../packages/runtime/README.md), SDK 대응과 오류 분류는 [Paseo Adapter](../packages/paseo-adapter/README.md)를 참고한다. [SDK API 문서](https://paseo.sh/docs/sdk/reference.md)

연결 실패만으로 Daemon이 종료됐다고 판단하지 않는다. 인증 실패와 버전 문제도 Daemon 미실행과 구분한다. 상태 조회 과정에서 Daemon을 자동 시작·재시작하거나 설정을 변경하지 않는다.

## 세션과 작업의 동작

### 생성과 요청 전달

- 세션 식별자는 CLI 프로세스가 종료된 뒤에도 같은 세션을 찾는 데 사용할 수 있어야 한다.
- 초기 구현에서는 세션 생성과 첫 요청 전달을 별도 동작으로 다루는 방안을 제안한다. CLI가 두 동작을 조합할 수 있으며, 생성 후 요청 전달에 실패하면 이미 생성된 세션 식별자와 실패를 함께 제공한다.
- 요청 전달은 접수 결과를 반환하고, 실행 완료는 관찰·대기를 통해 확인한다.
- 생성·요청 전달 중 연결이 끊겨 결과가 불명확하면 무조건 재전송하지 않는다. 중복 세션·중복 작업을 방지할 식별·확인 경로를 검증한다.
- 실행 중인 세션에 후속 요청을 보낼 때 대기열에 넣을지, 거절할지, 진행 중인 작업에 개입할지는 구현 전 확인 항목이다. 기존 작업을 묵시적으로 중단하지 않는다.

### 관찰과 재접속

- 세션 상태와 개별 작업의 실행 결과를 구분한다. 세션이 대기 상태로 바뀐 사실만으로 특정 작업의 성공을 판단하지 않는다.
- 작업 완료는 해당 작업의 완료·실패·취소 이벤트와 연결해 판단한다. 요청과 작업 식별자의 대응 방법을 확인한다.
- 대기 시간 초과는 관찰을 기다리던 호출의 결과다. 에이전트 작업의 취소나 종료를 뜻하지 않는다.
- 권한 요청으로 대기가 반환되더라도 작업이 완료됐다고 처리하지 않는다. 응답 후 해당 작업을 계속 관찰할 수 있어야 한다.
- 초기 상태·이력 조회와 이벤트 구독을 조합하되, 초기화 사이에 발생한 변경을 놓치지 않도록 설계한다. 재접속 시 상태와 구독을 복구하며, 필요한 이력을 다시 가져온다. 이벤트 누락·중복·이력 교체의 처리 방법을 검증한다.
- 구독 해제와 CLI 연결 종료는 세션을 보관하거나 중단하지 않는다.

Paseo SDK는 요청 접수와 작업 결과 대기를 구분하고, 시간 초과가 Agent를 취소하지 않는다고 설명한다. 이벤트 문서는 작업 종료 이벤트로 완료를 판단하며, 구독 복구와 이력 교체를 처리하도록 안내한다. [세션 문서](https://paseo.sh/docs/sdk/agents.md), [이벤트 문서](https://paseo.sh/docs/sdk/events.md)

### 권한·중단·보관

- 권한 요청은 대상 세션·요청 ID와 응답을 연결한다. 이미 처리되거나 유효하지 않은 요청에 대한 응답 결과도 구분한다.
- CLI의 비대화형 호출은 권한 대기 정보를 구조화해 반환하고, 후속 명령에서 응답할 수 있도록 한다. 자동 승인으로 대기를 해소하지 않는다.
- 현재 작업 중단은 세션 영구 삭제와 구분한다. 중단 후에도 세션을 조회하고 후속 작업에 사용할 수 있는지 검증한다.
- 세션 보관은 기록을 남기는 정리 동작이다. 보관 결과와 이미 보관된 세션에 대한 재요청 동작을 확인한다.
- 작업 공간 보관과 파일·worktree 삭제를 세션 보관에 임의로 덧붙이지 않는다. Paseo 자체의 부모·자식 및 작업 공간 정리 동작을 확인하고, 의도한 범위에만 적용한다.
- 에이전트 실행 이력과 현재 실행 상태의 원본은 Daemon으로 유지하는 방안을 제안한다. Adapter는 조회·변환에 필요한 값을 다루며 별도 세션 상태 저장소를 만들지 않는다. Core가 관리할 Module·Workspace 연결 정보와는 구분한다.

## SDK 대응 경로와 확인이 필요한 부분

다음은 2026-09-10에 열람한 공개 문서의 대응 후보다. 개발 검증 환경은 CLI·SDK·Daemon 모두 `0.8.0-beta.1`을 사용한다. 기능별 연동 검증은 별도로 수행하며, 메서드 존재만으로 성공을 판단하지 않는다. [SDK API 문서](https://paseo.sh/docs/sdk/reference.md)

| 기능 | 문서에서 확인한 경로 또는 추가 확인 사항 |
| --- | --- |
| 연결 관리 | `connect()`, `getConnectionState()`, `close()` 및 연결 제한 시간·재연결 설정. `close()` 이후에는 새 client가 필요하다. |
| Daemon 상태 조회 | `paseo status`는 로컬 조회다. Adapter는 내부 `DaemonClient`의 `getLastServerInfoMessage()`와 `getDaemonStatus()`를 사용한다. 반환 계약과 오류·버전 판정은 [구현 안내](../packages/paseo-adapter/README.md)를 참고한다. |
| Provider·모델·모드 | `client.providers.listAvailable()`, `listModels()`, `listModes()`. 전체 진단 기능의 구현은 초기 범위에서 제외한다. |
| 실행 작업 공간 | `client.workspaces.list()`, `open(cwd)`, `ref()`, `create()`. `open()`은 기존 공간을 재사용하거나 생성할 수 있으므로 읽기 전용 조회에 사용하지 않는다. |
| 세션 생성 | `workspace.agents.create()` 또는 `client.agents.create()`. 후자는 디렉터리에 새 작업 공간을 생성하는 동작이므로 배치 정책을 확인한다. |
| 세션 조회 | `client.agents.list()`, `ref()`와 Agent handle의 `refresh()`. `ref()`만으로는 서버 조회가 일어나지 않는다. |
| 요청 전달·결과 대기 | Agent handle의 `send()`, `run()`, `waitForFinish()`. 요청 접수·완료 이벤트·후속 요청의 대응을 확인한다. |
| 상태·이력 관찰 | Agent handle의 `subscribe()`, `timeline.refetch()`, `timeline.subscribe()`. 디렉터리 구독 초기화와 타임라인 구독 준비 완료를 확인한다. |
| 권한 요청 | `pendingPermissions`와 `respondToPermission()`. 지원하는 요청·응답 형식을 실제 Provider에서 확인한다. |
| 현재 작업 중단 | 조사한 공개 Agent handle 메서드 목록에서는 대응 메서드가 확인되지 않았다. 선택한 SDK 버전과 `paseo stop`이 사용하는 daemon API·구현을 추가 조사한다. |
| 세션 보관 | Agent handle의 `archive()`. 하위 Agent에 대한 적용 범위와 자원 정리 동작은 사용할 버전에서 검증한다. |

## 이번 범위에 포함하지 않는 기능

- Daemon 설치·시작·종료·재시작·설정 변경, 페어링 관리, 다중 Daemon 운영.
- Heartbeat와 schedule의 생성·제어.
- 터미널 제어와 Workspace 스크립트·서비스 실행.
- Git worktree 격리·복제·프로젝트 등록 관리.
- 외부 Provider 세션 가져오기, 세션 영구 삭제, 보관된 세션 복원, 세션 프로세스 강제 재시작, 부모 관계 해제.
- 실행 중 모델·설정 변경의 전체 기능, Provider 설치·상세 진단, 플러그인·Hub·음성 기능.
- Module의 서비스 연결·검수 화면·Workflow·산출물 계약과 Worknaru Workspace 전체 모델.

세션 생성 때 필요한 실행 설정과 후속 메시지를 통한 같은 세션의 재사용은 초기 범위에 포함한다. 새 사용 사례에서 필요한 기능이 생기면 [전체 참고 목록](paseo-cli-capabilities.md)을 기준으로 범위를 검토한다.

## 검증할 시나리오

1. 정상 접속, 접속 실패, 인증 실패, 시간 초과를 구분한다. 원격 접근 실패를 로컬 Daemon 종료로 표시하지 않는다.
2. 선택한 Provider·모델과 실행 위치로 세션을 생성하고 식별자로 조회한다. 명령을 종료한 뒤 다시 연결해 같은 세션을 조회하고 후속 작업을 보낸다.
3. 요청 접수 뒤 해당 작업의 출력과 완료·실패를 확인한다. 이미 존재하는 과거 이력과 새 작업의 결과를 혼동하지 않는다.
4. 권한 요청을 확인하고 승인 또는 거부를 전달한 뒤 해당 작업의 후속 상태를 관찰한다.
5. 대기 시간이 초과돼도 세션을 다시 조회할 수 있다. 시간 초과를 취소로 표시하지 않는다.
6. 실행 중인 작업을 중단하고 확인된 결과를 반환한다. 중단 거절·시간 초과를 성공으로 표시하지 않는다.
7. 연결이 끊겼다가 복구됐을 때 상태·관찰을 복구한다. 결과가 불명확한 요청을 무조건 재전송하지 않는다.
8. 세션을 보관한 뒤 조회 가능한 기록과 정리된 실행 자원을 확인한다. 다른 세션·작업 공간에 의도하지 않은 정리가 발생하지 않는지 확인한다.
9. Core와 CLI에는 Paseo SDK 타입·응답·예외가 직접 노출되지 않는다. CLI는 Worknaru가 정의한 결과와 오류로 JSON 출력 및 종료 코드를 결정한다.

## 구현 전 먼저 확인할 사항

- [개발 환경](../apps/paseo-dev/README.md)에서 정한 데이터 저장 위치·접속 주소·버전 조합의 제품 Adapter 적용 방법과 실제 Provider 인증 사용 확인.
- 작업 중단의 구체적인 연동 경로. Daemon 상태 조회는 [첫 구현](../packages/paseo-adapter/README.md)을 기준으로 후속 기능과 연결한다.
- 요청과 개별 작업의 식별·대응, 실행 중 요청 처리, 연결 단절 뒤 중복 요청 방지 가능 범위.
- 실행 위치 선택, 부모·자식 관계, 세션 보관 시 자원 정리 범위.

첫 구현인 Daemon 상태 조회의 계약과 사용법은 [Runtime](../packages/runtime/README.md)과 [Paseo Adapter](../packages/paseo-adapter/README.md)에 둔다. 이후 필요한 세션 관리 기능을 순차적으로 추가한다.
